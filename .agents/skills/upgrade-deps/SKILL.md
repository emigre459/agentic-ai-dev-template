# Upgrade Deps

## Overview

One PR that brings every dependency current, security fixes first, with the same rigor as feature work. Dependency PRs land one at a time otherwise, and each costs a round of catching up with `main`; this skill folds them into one branch, regenerates every lockfile with the ecosystem's own tool, fixes what the bumps break, and proves each security alert is actually fixed before the PR opens.

**Delegations:**
- The branch, when there is an issue card → `build-from-issue` (this skill is its build step for a dependency card)
- Per-fix discipline when a bump breaks code → `superpowers:test-driven-development`; non-obvious breakage → `superpowers:systematic-debugging`
- Fresh evidence before any "it's green" claim → `superpowers:verification-before-completion`
- The PR after it opens → `resolve-pr-concerns`

**Bundled script** (run it from the repo root; path is relative to this skill's directory, e.g. `${CLAUDE_SKILL_DIR}` in Claude Code, `.agents/skills/upgrade-deps/` canonically):

```bash
python3 <skill-dir>/scripts/alert_status.py --repo <owner>/<repo>
```

It reads the open Dependabot alerts and tests every version locked in each alert's lockfile (nested copies included) against the alert's vulnerable range. Per alert: `cleared`, `open`, or `unknown` (lockfile or range unreadable). Exit 0 only when every alert is `cleared`; 1 otherwise; 64 when `gh` fails. Run it before and after — the Dependabot UI only catches up once the fix reaches the default branch, so on a refresh branch this script is the check.

## Rules

- **Lockfiles are regenerated, never hand-edited and never copied from a bot PR.** A bot PR tells you *what* to bump; its lockfile diff is against an older base and its siblings. Apply the manifest change, then run the tool (`uv lock`, `bun install` / `bun update`).
- **Security first, and never deferred.** If a security fix can't land, stop and ask the user. Never downgrade or skip it to get green.
- **Fix breakage; don't suppress it.** A new lint rule gets fixed, a config gets migrated, a changed API gets updated. Ignoring a rule, skipping a test, or loosening a check needs the user's explicit approval.
- **One PR.** Not one per ecosystem or per risk group.
- **Never auto-merge, force-push, or close a bot PR before the refresh merges.**

## Step 0: Branch

- With an issue card: run this inside `build-from-issue` (its linked branch, spec, and acceptance audit apply).
- Without one: a fresh branch off the latest `main` (`git fetch origin && git switch -c deps-refresh-<YYYY-MM-DD> origin/main`), clean tree.
- Push after every commit (`push-every-commit` rule).

## Step 1: Inventory

```bash
gh pr list --repo <owner>/<repo> --state open --json number,title,author,headRefName,files \
  --jq '.[] | select(.author.login | test("dependabot|renovate"))'
python3 <skill-dir>/scripts/alert_status.py --repo <owner>/<repo>
gh pr list --repo <owner>/<repo> --state merged --search "upgrade-deps in:body" --limit 1 --json number,body
```

- **Bot PRs:** for each, `gh pr diff <n>` and note the *manifest* changes (version ranges in `pyproject.toml` / `package.json`, a `[build-system]` requirement, a workflow `uses:` pin). Their lockfile changes are ignored (Rules).
- **Alerts:** the `open` set from `alert_status.py` is the security work. An alert with no bot PR still counts; Dependabot can miss a lockfile it can't update.
- **Ecosystems:** every `directory` in `.github/dependabot.yml`, plus any `uv.lock` / `bun.lock` not listed there. Each uv project and each bun project is bumped separately.
- **Previous refresh:** the last merged refresh PR's body lists majors it deferred and why — retry them; that body is this skill's only state between runs.

## Step 2: Security fixes

For each `open` alert, cheapest fix first:

1. **Unused?** Remove the dependency.
2. **Direct dependency?** Raise its floor in the manifest to at least `first_patched`, then relock.
3. **Transitive?** Targeted upgrade: `uv lock --upgrade-package <pkg>` in that uv project; `bun update <pkg>` (or update the parent that pins it) in that bun project.
4. **Still pinned below the fix by a parent?** An override, as the last resort — bun `overrides` in `package.json`, uv `constraint-dependencies` under `[tool.uv]` — with the reason in the PR body.

Re-run `alert_status.py`; every alert you worked must read `cleared`. Commit the slice ("security: …") and push.

## Step 3: Fold the bot PRs

Apply each bot PR's manifest change, then relock with the tool. Keep the groups `.github/dependabot.yml` couples (e.g. a bundler and its plugin, a test runner and its coverage package) moving together. Commit ("deps: fold #<n>, #<m> …") and push.

## Step 4: Bump everything else

- **uv projects:** `uv lock --upgrade` in each. It never touches `[build-system] requires` (build requirements aren't locked): bump those only by editing the manifest, as a bot PR proposes.
- **bun projects:** `bun update --latest` in each (this crosses majors and rewrites `package.json` ranges).
- **GitHub Actions:** only the `uses:` pins a bot PR proposed; there is no relock tool.
- Then `make deps` so the environment matches the locks.

Commit ("deps: routine bumps") and push. Note every major version crossed — Step 5 decides whether each one stays.

## Step 5: Fix what broke

```bash
make pr_check && make coverage && make security
```

Read the failures, not just the exit codes. Typical, mechanical breakage:

- **A linter's new default rules** (e.g. a ruff release adding import-order or `subprocess` `check=` findings): fix each finding; `--fix` for the auto-fixable ones, by hand for the rest. Read every *unsafe* auto-fix against the file's own constraints before keeping it — e.g. rewriting a type alias to `type X = ...` is a SyntaxError on the older interpreter a stdlib-only script promises to run under; find the form that satisfies both.
- **A config schema bump** (e.g. Biome asking for `biome migrate`): run the tool's migration.
- **A changed API in a major:** update the call sites with TDD.

**Rollback, one bump at a time:** a *non-security* major whose breakage isn't mechanical (needs a design change, or the user's call) is rolled back alone — pin it to its previous major, relock — and listed as deferred with the reason. The rest of the run continues. A security fix is never rolled back (Rules).

Commit fixes separately from bumps ("fix: … for <pkg> <version>") and push.

## Step 6: Verify

Fresh, in this order, and read the output:

```bash
make deps
make pr_check
make coverage
make security
python3 <skill-dir>/scripts/alert_status.py --repo <owner>/<repo>   # must exit 0
```

`make security` covers what each stack's scanner covers (a JS dependency audit, a Python SAST scan); `alert_status.py` covers the Dependabot alerts across every lockfile.

## Step 7: PR, then hand off

Open one PR (via `build-from-issue`'s finalize step when there's a card). Body:

```markdown
Closes #<issue>   <!-- if any -->
<!-- upgrade-deps -->

## Supersedes
- #<n> <title>   (one per folded bot PR)

## Security alerts cleared
| Alert | Package | Was | Now | Fix |
|---|---|---|---|---|

## Notable bumps
- <majors crossed, and what each needed>

## Deferred
- <pkg> <from> → <to>: <why> (or "None")
```

The `<!-- upgrade-deps -->` marker lets the next run find this body (Step 1). Then invoke `resolve-pr-concerns`. After the PR merges, Dependabot closes the PRs it superseded; close any it didn't with a comment linking the merged PR (`gh pr close <n> --comment "Folded into #<pr>."`).

## Red flags

- Editing a lockfile by hand, or checking out a bot PR's lockfile.
- An `open` or `unknown` alert left at Step 6 without the user deciding.
- A lint rule ignored, a test skipped, or a check loosened to get green, without approval.
- A security fix deferred or downgraded.
- One major's breakage abandoning the whole run instead of rolling back that one bump.
- Closing a bot PR before the refresh merges.
- Claiming "all green" without fresh Step 6 output.
